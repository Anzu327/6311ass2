更新：2026-10-05。本文面向搭档及搭档使用的 GPT / Codex。

仓库：[Anzu327/6311ass2](https://github.com/Anzu327/6311ass2)。开始工作时以当前仓库代码和根目录 `AGENTS.md` 为准。

## 1. 我们在设计什么

FOR YOU 是参考 TikTok / Douyin 界面语法的互动艺术作品，核心问题是：**平台是在理解我们，还是在塑造我们？**

平台在观众表达兴趣前随机分配身份，然后用越来越单一的推荐强化它。观众否认或要求重置，系统回应，却保留原来的身份。这个故意失效的反馈机制用于讨论算法凝视、身份包装和选择权，不代表 TikTok 实际采用人脸分析来判断人格。

作品界面使用英文，开发和交接文档使用中文。

### 体验流程

1. **进入**：选择摄像头或示例模式，看到 “Made for you.”。
2. **模拟扫描**：扫描线、进度和系统语言制造被分析的感觉。
3. **被定义**：显示 “WE KNOW YOU.” 和随机身份；“This is not me” 只增加否认次数，不改变身份。
4. **六条推荐**：从看似贴心的内容逐渐进入重复、商业化和身份锁定。
5. **重置失败**：点击 “Reset my profile”，重新扫描后进入 “Same result.” 结尾，保留当次身份。
6. **解释与重启**：解释标签是随机赋予的；“Start again” 开始新的体验。

刷到第六条不会自动进入结尾；目前结尾由重置操作触发。上滑、滚轮及上下方向键可切换帖子。

### 三种身份与内容结构

| 身份 | 主题 | 身份强调色 |
| --- | --- | --- |
| SOFT DREAMER | 敏感、创造、逃避、理想化生活 | 青色 `#53f5ed` |
| TECH OPTIMIZER | 效率、控制、升级、产出 | 黄绿色 `#b7ff66` |
| CULTURE CURATOR | 品味、怀旧、区分、策展 | 粉色 `#ff9ece` |

每种身份固定六条帖子：前三条逐渐收窄兴趣，第四条是明确标注的虚构广告，最后两条加强重复和分类锁定。评论和互动数字也是作品中的虚构数据。

### 视觉与界面原则

- **只保留 TikTok 风格应用界面**。不要恢复侧边导航、作品说明侧栏或应用外的技术说明。
- 桌面是深色背景上的居中竖屏舞台；手机填满视口，并预留顶部和底部安全区。
- 顶部是 Following / For You、摄像头状态及作品说明入口；右侧是头像、点赞、评论和分享；底部是 Home / Explore / 创建 / Inbox / Profile。
- 人像或自拍是画面背景，深色渐变保证文字可读。大标题使用 DM Sans，系统标签使用 Space Mono。
- 主色是黑、白、青色和红色 `#fe2858`，再用身份色区分分类。
- Glitch 随推荐推进逐渐增强：重复文字、标签覆盖、灰度、高对比和文字错位。故障应表达分类越来越僵硬的过程。
- 已选定的生成设计图若随交接提供，应作为布局、密度、间距、字体、颜色和内容层级的视觉依据；未拿到该图时，不假装已经看过。

### 摄像头与人脸特效

摄像头由观众主动开启，不请求麦克风。MediaPipe Face Landmarker 在浏览器中检测脸的位置，让特效随脸移动；柔和身份使用腮红，科技与文化身份使用眼部扫描装饰。

**检测脸的位置不等于识别个人，也不根据外貌推断人格。** 摄像头帧和关键点不上传、不保存。没有摄像头可使用 AI 生成的虚构成年人物肖像；示例肖像不做人脸跟踪。无脸时隐藏特效，模型失败时仍保留自拍与作品流程。

## 3. 本地客户端如何编辑 GitHub 项目

**Codex 客户端在你的电脑上运行，不代表文件一定在你的电脑上。** 文件位置取决于当前聊天选择的执行环境：

| 方式 | 文件在哪里 | 如何更新 GitHub |
| --- | --- | --- |
| Codex 客户端连接云端环境 | 云端工作区；本次工作区为 `/workspace/6311ass2` | 在云端提交、推送分支，再创建 PR |
| Codex 客户端打开本地克隆 | 搭档电脑上的项目目录 | 在本地提交、推送分支，再创建 PR |
| GitHub Codespaces | GitHub 提供的独立云端开发环境 | 在 Codespace 内提交、推送分支，再创建 PR |

这些方式可以协作，但不是同一个实时共享文件夹。**保存文件 ≠ Git commit ≠ Git push ≠ PR 合并。** 云端工作区中的未提交修改也不会自动出现在搭档的环境中。

普通 GPT 聊天仅收到仓库链接时，不一定能读写项目。要实际操作，需要有文件/终端工具的 Codex 环境，或当前已授权且支持相应操作的连接器。GitHub 连接器授权也不等于终端 Git 已完成认证。

### 路线 A：本地 Codex 客户端连接云端工作区

1. 仓库拥有者在 GitHub 仓库 **Settings → Collaborators → Add people** 邀请搭档；搭档用自己的账号接受邀请。
2. 搭档在自己的 Codex 账号中配置 GitHub 访问，并授权本仓库（如果当前环境选择流程要求连接 GitHub）。
3. 在客户端创建或选择绑定本仓库的云端环境，再让聊天使用该环境。具体入口名称以搭档客户端版本为准；不要把“打开本地文件夹”当成已连接云端。
4. 等环境运行就绪，请 GPT 检查工作目录、仓库远程地址、分支和未提交修改。云端路径可能与本次不同，无需强行改成 `/workspace/6311ass2`。
5. 确认远程仓库是本项目后，从最新 `main` 创建独立功能分支，编辑、检查，再提交和推送。
6. 创建 PR，由另一位搭档审阅并合并；下一轮工作前同步合并后的 `main`。

如果客户端没有云端环境入口，可使用路线 B，或在 GitHub 仓库 **Code → Codespaces** 创建自己的 Codespace。Codespace 与 Codex 云端环境是不同产品环境，不会自动互通未提交文件。

### 路线 B：本地克隆后让 Codex 编辑

1. 接受仓库邀请，用自己的 GitHub 账号完成本机 Git 认证，可通过 GitHub Desktop 或 GitHub CLI 等方式配置。
2. 用 GitHub Desktop 克隆仓库，或让有终端工具的 GPT 执行：

   ```bash
   git clone https://github.com/Anzu327/6311ass2.git
   ```

3. 在 Codex 客户端打开克隆得到的 `6311ass2` 项目文件夹，让聊天使用本地环境。
4. 请 GPT 读取 `AGENTS.md` 和本文，再从最新 `main` 建功能分支并修改文件。
5. 请 GPT 完成检查、提交、推送及 PR。合并后，在本地拉取最新 `main`。

搭档只需自行完成账号登录、接受邀请、环境选择及必要的系统授权；文件编辑、命令执行和预览应由具备工具的 GPT 执行。不要共享账号、密码或令牌，也不要把令牌贴进聊天。

## 4. 给搭档的 GPT / Codex 的操作要求

请先向搭档说明当前属于云端工作区、本地克隆还是仅有聊天；根据实际可用工具操作，不假定自己拥有 GitHub 写权限，也不编造客户端菜单。

1. 读取根目录 `AGENTS.md`、本文及相关代码。检查 `pwd`、`git status --short`、`git remote -v`、`git branch --show-current`，确认目标仓库及已有修改。
2. 保护已有修改。工作区干净且远程访问正常时，同步 `main` 并创建搭档自己的分支，例如 `feature/feed-content-<唯一后缀>`。有未提交工作或分支已有提交时，先判断归属，不能直接 reset、覆盖或切换丢弃。
3. 按搭档的实际需求编辑对应文件；修改文案时保留三种身份及六条推荐结构，修改流程时先读取状态逻辑。
4. 做实质视觉修改前，若视觉来源不明确或与目标不符，按 `AGENTS.md` 使用 Product Design 的 `get-context` 工作流；当前插件若没有此技能，先检查可用入口并说明缺失，不假装已执行。记录搭档确认的长期设计偏好到 `AGENTS.md`。
5. 需要验证界面时，自己安装依赖、启动开发服务器并使用环境浏览器打开预览，不把可以代办的启动步骤交给搭档。通常使用 `npm ci` 和 `npm run dev -- --host 0.0.0.0`；按环境提供的预览方式访问实际端口。摄像头需要 HTTPS 或 localhost。
6. 代码修改运行 `npm run typecheck`、`npm test`、`npm run build`、`npm run test:sites`，报告真实结果。纯 Markdown 修改检查内容和链接即可，不必启动应用。
7. Sites 交接前必须完成 build 和 test:sites，并确认存在 `dist/client/index.html`、`dist/server/index.js`、`dist/.openai/hosting.json`。
8. 检查 diff，只提交本次相关文件。搭档要求提交、推送或创建 PR 时执行相应步骤，不将 PR 创建当成已合并，不强制推送覆盖他人工作。
9. 权限或网络失败时，说明失败操作和原因，并指导搭档完成所缺的授权或环境设置；不要索取密码、伪造成功状态或声称本地修改已经同步到 GitHub。
10. 最后告诉搭档：改了哪些文件、检查结果、保存在哪个环境、是否已 commit / push / 创建 PR，并给出实际 PR 链接（如有）。

## 5. 两人协作时的交接

各自使用独立环境和分支。开始一轮工作前同步 `main`，PR 合并后再同步一次。两人需要改同一文件时先约定范围；冲突解决后重新检查，不覆盖搭档的提交。
