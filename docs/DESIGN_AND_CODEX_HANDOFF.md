## 1. 我们在设计什么

FOR YOU 是参考 TikTok / Douyin 界面语法的互动艺术作品，核心问题是：**平台是在理解我们，还是在塑造我们？**

平台在观众表达兴趣前随机分配身份，然后用越来越单一的推荐强化它。观众否认或要求重置，系统回应，却保留原来的身份。这个故意失效的反馈机制用于讨论算法凝视、身份包装和选择权，不代表 TikTok 实际采用人脸分析来判断人格。

作品界面使用英文，开发和交接文档使用中文。

### 体验流程

1. **进入**：选择摄像头或示例模式，看到 “Made for you.”。
2. **模拟扫描**：扫描线、进度和系统语言制造被分析的感觉。
3. **被定义**：显示 “WE KNOW YOU.” 和随机身份；“This is not me” 只增加否认次数，不改变身份。
4. **六条推荐**：从看似贴心的内容逐渐进入重复、商业化和身份锁定。
5. **重置失败**：点击 “Reset my profile”，重新扫描后进入 “Same result.” 结尾，保留当次身份。
6. **解释与重启**：解释标签是随机赋予的；“Start again” 开始新的体验。

刷到第六条不会自动进入结尾；目前结尾由重置操作触发。上滑、滚轮及上下方向键可切换帖子。

### 三种身份与内容结构

| 身份 | 主题 | 身份强调色 |
| --- | --- | --- |
| SOFT DREAMER | 敏感、创造、逃避、理想化生活 | 青色 `#53f5ed` |
| TECH OPTIMIZER | 效率、控制、升级、产出 | 黄绿色 `#b7ff66` |
| CULTURE CURATOR | 品味、怀旧、区分、策展 | 粉色 `#ff9ece` |

每种身份固定六条帖子：前三条逐渐收窄兴趣，第四条是明确标注的虚构广告，最后两条加强重复和分类锁定。评论和互动数字也是作品中的虚构数据。

### 视觉与界面原则

- **只保留 TikTok 风格应用界面**。不要恢复侧边导航、作品说明侧栏或应用外的技术说明。
- 桌面是深色背景上的居中竖屏舞台；手机填满视口，并预留顶部和底部安全区。
- 顶部是 Following / For You、摄像头状态及作品说明入口；右侧是头像、点赞、评论和分享；底部是 Home / Explore / 创建 / Inbox / Profile。
- 人像或自拍是画面背景，深色渐变保证文字可读。大标题使用 DM Sans，系统标签使用 Space Mono。
- 主色是黑、白、青色和红色 `#fe2858`，再用身份色区分分类。
- Glitch 随推荐推进逐渐增强：重复文字、标签覆盖、灰度、高对比和文字错位。故障应表达分类越来越僵硬的过程。
- 已选定的生成设计图若随交接提供，应作为布局、密度、间距、字体、颜色和内容层级的视觉依据；未拿到该图时，不假装已经看过。

### 摄像头与人脸特效

摄像头由观众主动开启，不请求麦克风。MediaPipe Face Landmarker 在浏览器中检测脸的位置，让特效随脸移动；柔和身份使用腮红，科技与文化身份使用眼部扫描装饰。

**检测脸的位置不等于识别个人，也不根据外貌推断人格。** 摄像头帧和关键点不上传、不保存。没有摄像头可使用 AI 生成的虚构成年人物肖像；示例肖像不做人脸跟踪。无脸时隐藏特效，模型失败时仍保留自拍与作品流程。

## 3. 首选方式：本地 Codex 客户端连接云端

**优先使用电脑上的 Codex 客户端连接本仓库的云端工作区。所有项目文件在云端编辑，不在电脑上克隆或编辑本地副本。** 客户端是操作入口，实际读写、命令执行和应用预览都在云端环境中进行。本次云端路径是 `/workspace/6311ass2`，搭档的路径以其实际环境为准。

### 搭档需要亲自完成的设置

1. 接受仓库拥有者发出的 GitHub Collaborator 邀请，使用自己的账号。
2. 在自己的 Codex 账号中配置 GitHub 访问，授权 `Anzu327/6311ass2`（如环境配置要求）。
3. 在本地 Codex 客户端创建或选择绑定本仓库的云端环境，并让聊天使用它。具体入口名称以客户端版本为准。
4. 等环境就绪，让 GPT 检查工作目录和 Git 远程地址，确认正在操作云端仓库。仅打开电脑上的项目文件夹不满足此要求。

如果当前客户端没有云端环境入口，请 GPT 说明实际缺少的功能并协助配置。可用 GitHub Codespaces 作为云端编辑的备选，但不要自动改成在电脑上克隆和编辑。Codespaces 与 Codex 云端工作区是独立环境，不会互通未提交文件。

普通 GPT 聊天仅收到仓库链接，不一定具备文件读写能力。请使用有文件及终端工具的 Codex 云端环境。GitHub 连接器授权也不等于云端终端 Git 已认证；GPT 应检查实际可用能力。

搭档自行完成账号登录、接受邀请、环境选择及必要授权；文件编辑、命令执行、检查和预览由 GPT 代办。不要共享密码或令牌。

### 每轮编辑后的同步要求

**每次编辑完成并检查无误后，GPT 都应主动提交本轮修改，并推送到 GitHub 的 `main`，不必等待搭档再提醒。** 保存到工作区或仅生成 commit 都不算完成同步；以远程 `main` 已包含本轮修改为准。默认不以功能分支或未合并 PR 作为最终交付。

开始编辑前读取最新 `main`。推送前再次检查远程是否被搭档更新；如有新提交，保留双方修改、解决冲突并重新检查，然后正常推送。不能强制推送覆盖搭档的工作。若当前环境使用 `work` 等分支，可将检查通过的本轮提交正常推送到远程 `main`，无需为了分支名字破坏已有工作。

如权限、网络或分支保护阻止更新 `main`，明确报告阻碍和所需操作，不声称同步成功。分支保护若要求 PR，可按该规则完成必要流程，检查通过后让修改进入 `main`；无法合并时明确说明尚未完成。

## 4. 给搭档的 GPT / Codex 的操作要求

1. 先向搭档说明：优先使用本地 Codex 客户端连接云端，项目文件在云端编辑。确认实际执行环境；如果只有普通聊天或本地目录，先指导搭档连接云端，不开始编辑本地副本。
2. 读取 `AGENTS.md`、本文及相关代码。检查 `pwd`、`git status --short`、`git remote -v`、`git branch --show-current`，确认目标仓库和已有修改。同步最新 `main` 时保护未提交文件及已有提交，不能直接 reset 或覆盖。
3. 不设固定分工。按搭档本轮需求编辑对应文件；改内容时保留三种身份及六条推荐结构，改流程时先读取状态逻辑。
4. 做实质视觉修改前，若视觉来源不明确或与目标不符，按 `AGENTS.md` 使用 Product Design 的 `get-context` 工作流；技能不可用时说明缺失，不假装已执行。长期设计偏好记录到 `AGENTS.md`。
5. 需要验证界面时，自己在云端安装依赖、启动开发服务器并通过环境浏览器打开预览。通常使用 `npm ci` 和 `npm run dev -- --host 0.0.0.0`，按环境提供的预览方式访问实际端口。摄像头需要 HTTPS 或 localhost。
6. 代码修改运行 `npm run typecheck`、`npm test`、`npm run build`、`npm run test:sites`，报告真实结果；涉及界面或交互还需预览验证。纯 Markdown 修改检查内容、链接和 diff 即可，不必启动应用。检查失败先修复再提交。
7. Sites 交接前完成 build 和 test:sites，并确认存在 `dist/client/index.html`、`dist/server/index.js`、`dist/.openai/hosting.json`。
8. 每次编辑完成并检查无误后，检查 diff、只提交本轮相关文件，并主动推送到远程 `main`。推送前检查远程新提交，必要时整合、解决冲突并重新验证；不强制推送。
9. 终端 Git 不可用时，可使用已授权的 GitHub 工具，基于最新远程 `main` 创建只包含本轮修改的提交，正常更新 `main` 并读回验证。权限或网络失败时说明实际原因，指导搭档完成所缺设置，不索取密码或令牌。
10. 最后报告修改文件、检查结果、云端保存位置、远程 `main` 是否已更新，并提供真实提交链接。未成功同步时明确说明，不把仅保存、仅提交或未合并 PR 当作完成。

两人各自使用云端环境，不设固定分工。每轮从最新 `main` 开始，编辑并检查通过后提交、推送到 `main`。同时修改同一文件时先约定范围；远程有新修改时整合双方工作并重新检查。GitHub 不会实时同步正在输入的代码。
